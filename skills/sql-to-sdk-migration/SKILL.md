# SQL → SDK 迁移

迁移的是访问接口，不是计算位置。原来一条 SQL 在数据库内完成的工作，换成 SDK 后仍应尽量在数据库内完成。

**第一性原理：** 从业务需要的结果、权限范围和原子性出发，判断哪些工作必须发生。
**奥卡姆剃刀：** 优先用已有能力直接表达。每增加一次读取、检查、事务或缓存，都要有具体理由；缺能力就补最小公共能力，不在 App 堆补丁。

## 先还原 SQL 的业务语义

- 一行代表什么；关联是一对一还是一对多；缺失关联、重复记录和版本优先级如何处理。
- 哪些条件决定可见范围；关联记录是否也受站点、租户或业务角色约束。
- NULL、缺失字段、大小写、排序规则、时区、日期边界和数值精度是否等价。
- 去重、聚合、排序、分页的先后顺序；总数统计的是分页前哪一层结果。
- 哪些写入必须一起成功；哪些状态或版本条件必须与写入原子判断。

`COUNT(DISTINCT order_id)` 要去重，不代表 `SUM(quantity)` 也应该先去重；跨站点 distinct 不能直接相加。不能为适应 SDK 改掉统计口径。

## 把集合运算留在数据库

| 需求 | 迁移方式 |
| --- | --- |
| 筛选、投影、排序、分页 | 同一次数据库查询完成，只返回需要的字段和页 |
| 关联、有效版本选择 | 服务端关联、子查询或管道，避免逐行查关系、层层收集 ID |
| count、distinct、group、sum | 返回数据库聚合结果，不下载明细计算 |
| 当前页补主数据 | 仅当关联不影响筛选、排序、行数与统计时，先分页再批量补充 |
| 完整导出 | 稳定排序并遍历最终结果；跨页一致性遵循原业务要求 |

下推也可能很慢：lookup 先生成巨大数组再过滤、对全量结果编号后才取小页，仍会做大量无效工作。看最终 SQL 的过滤、关联与 LIMIT 位置，不只看返回了多少行。

## 不把接口限制变成业务架构

核对实际安装的 SDK 和目标后端契约，区分“后端能做但 SDK 未暴露”和“后端没有能力”。优先补已有查询能力，不自行造 SQL 解析器或另一套 ORM。

返回分页、ID 数量、请求字节、表达式复杂度和执行期限是不同限制。统计十万行只需返回一个数，不需要分页下载十万行。不要沿用旧注释里的 100/200 个 ID 分批规则。

必须拆分时，先判断结果能否组合：全局 distinct、排序、分页、关联与原子写入不能简单逐批处理。优先表达关系，避免把中间 ID 集合带回 App 再传给数据库。

`queryBatch` 减少往返，里面仍有多条查询；不能消除重复扫描，也不保证后续分页共用快照。复用同次操作的身份、授权范围和公共读取，不用无界并发弥补过多请求。

## 事务只保护真实的不变量

- 普通展示保留鉴权和服务端范围过滤，读完即可返回；不默认追加全记录版本检查事务。
- 多个读取确实需要同一时刻的数据时，使用已有快照能力；不要事后逐行检查来模拟快照。
- 审批、发布、多记录状态流转，把必要的状态检查与变更放进同一原子操作。事务边界是业务动作，不是每行一个或整页所有操作一个。
- 保留并发冲突和幂等语义。写入超时不代表回滚，结果未知时不能换键重新执行。
- 页面读取不顺带修复历史、重建汇总或重复初始化集合。

## 性能看实际数据工作量

分别定位 App 串行等待、SDK 往返、服务端排队/连接池等待、SQL 执行和结果传输。请求少不等于查询快，SQL 首批时间不等于整页时间。

- **往返多：** 消除 N+1、重复身份/字典读取及无必要的 ID 分片。
- **扫描或关联膨胀：** 检查过滤位置、关联基数、投影宽度、排序及 LIMIT 位置。
- **索引无效：** 检查类型、表达式、选择性和多列顺序。保留唯一约束，不机械复制旧索引，也不按数量一概删除。
- **排队长：** 查看慢查询和后台任务占用，先减少工作量；增加并发或延长超时不会让 SQL 更便宜。

只有重复计算仍昂贵、且业务允许明确刷新周期时，才采用派生汇总。先改善查询，不默认给所有页面加缓存或定时任务。
