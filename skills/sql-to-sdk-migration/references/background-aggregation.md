# 后台聚合

后台计算改变计算发生的时间，不会自动减少总工作量。只有查询本身已合理、重复统计仍昂贵且业务允许延迟时，才引入派生结果。

## 哪些结果可以复用

- 明确来源、时间窗口、授权范围和计算口径。全站点汇总不自动适用于站点子集。
- 跨站点 distinct、版本优先级和去重结果未必可按站点或月份相加，先确定指标可组合性。
- 稳定历史事实与当前任务状态、逾期时间分别处理，避免无关时间戳使全部历史失效。
- 明确哪些来源变化需要刷新。缺失或过期时，实时重算、等待刷新、展示旧结果具有不同成本和业务语义。

## 只添加需要的机制

小结果能一次原子替换，就不要设计 generation、分片和 manifest。只有多记录结果无法一次原子写入时，才考虑先写不可见的新一代，再原子切换读取版本，避免读到半成品。

只有真实存在重复触发或多实例竞争时，才使用已有条件写或租约；不默认新增锁服务。读取页面不负责启动生成。

优先增量更新受影响范围，避免每个新月份重复扫描全部历史。旧结果的保留和清理按实际增长量决定，不预先引入通用缓存管理框架。

后台任务仍使用数据库连接；本机 nice/CPUWeight 不等于数据库低优先级。减少重复扫描与并发，避免刷新拖慢前台读取。

调度复用已明确支持 App 身份和生命周期的现有执行入口。平台尚无稳定入口时列为能力缺口，不在 SDK 自建调度器。任务启动、无变化检查和实际生成是不同状态，不能用检查耗时估算生成耗时。
